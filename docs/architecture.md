# معماری شبکه‌ی PerShiaA

## نگاه کلی

شبکه از یک هاب مرکزی و پنج گروه سرویس ساخته شده است. هاب هیچ منطق تحلیلی ندارد؛
فقط نیت را تشخیص می‌دهد، گام‌ها را می‌چیند و نتایج را جمع می‌کند. این تفکیک باعث می‌شود
هر سرویس مستقل تست‌پذیر و مستقل قابل‌جایگزینی باشد.

```
                        ┌───────────────────────┐
                        │   هاب (Orchestrator)  │
                        │  intent → plan → run  │
                        └───────────┬───────────┘
             ┌──────────────┬───────┴────────┬──────────────┐
             ▼              ▼                ▼              ▼
      ┌────────────┐ ┌────────────┐  ┌────────────┐ ┌────────────┐
      │  دکترین    │ │   OSINT    │  │   محتوا    │ │   انتشار   │
      │  تحلیل     │ │  منابع     │  │  ai_melli  │ │  bots/*    │
      │  + OCR     │ │  عمومی     │  │  گالری     │ │  تلگرام/…  │
      └────────────┘ └────────────┘  └────────────┘ └────────────┘
             │              │                │              │
             └──────────────┴────────────────┴──────────────┘
                            داده‌ی مشترک: ./data
```

## لایه‌ها

| لایه | مسئولیت | پوشه | وابستگی سنگین |
|------|---------|------|----------------|
| هسته‌ی تحلیلی | پرونده‌ی مستند، ۵۲ کنترل، دفتر منابع | `doctrine/` | اختیاری: pdfminer, Tesseract |
| حضور وب | سایت اندیشکده، نقشه ذهنی، نقشه راه | `web/` | ندارد |
| اطلاعات عمومی | DNS، متادیتای عمومی، گراف هویت | `osint/` | اختیاری: FastAPI |
| خودکارسازی | دانلود، ربات‌ها، کتابخانه‌ی پیام‌رسان | `bots/` | اختیاری: Telethon, Selenium, Node |
| تولید محتوا | متن، تصویر برداری، گالری | `ai/` | ندارد |
| هماهنگی | intent، plan، اجرا، گزارش | `hub/` | ندارد |

## جریان داده

1. کاربر یک درخواست طبیعی می‌دهد (CLI، داشبورد یا API).
2. هاب `detect_intents` را اجرا و `build_plan` را می‌سازد.
3. هر گام اجرا می‌شود. اگر سرویسِ API بالا نباشد، همان منطق درون‌فرآیندی اجرا می‌شود.
4. خروجی دکترین (dossier) به گام محتوا می‌رود و قاب‌های انتشار ساخته می‌شود.
5. گزارش نهایی با `summary`, `stages`, `dossier_id` برگردانده می‌شود.

## قراردادها

### برچسب اطمینان

| برچسب | معنا | شرط استفاده |
|-------|------|-------------|
| `[F]` | قطعی | سند و محل شاهد موجود است |
| `[H]` | احتمال بالا | چند منبع مستقل |
| `[M]` | احتمال متوسط | یک منبع یا شاهد ناقص |
| `[I]` | استنباط | نتیجه‌گیری تحلیلی بدون سند صریح |
| `[U]` | نامعلوم | نیازمند بررسی بیشتر |

### قطعیت و بازتولیدپذیری

- موتور دکترین **قطعی** است: دو اجرای یکسان روی یک پیکره، هش یکسان می‌دهد.
- مهر `integrity.sha256` روی پرونده‌ی کامل (بدون فیلد integrity) محاسبه می‌شود.
- ترتیب چک‌ها و متن‌ها ثابت است تا diff معنادار باشد.

### خرابی جزئی

`hub/defaults.partial_success = true`. یک گام خطادار وضعیت `error` می‌گیرد و اجرا ادامه می‌یابد.
گام‌های نیازمند راز (انتشار، دانلود واقعی) وضعیت `skipped` با دلیل صریح می‌گیرند.

## امنیت و حریم خصوصی

- پیش‌فرض سرورها `127.0.0.1`؛ باز کردن روی `0.0.0.0` تصمیم صریح اپراتور است.
- پویش PII فقط تعداد و نمونه‌ی **ماسک‌شده** برمی‌گرداند.
- ایمیل‌های کشف‌شده از تاریخچه‌ی کامیت همیشه ماسک می‌شوند.
- هیچ کلید یا نشستی در مخزن نوشته نمی‌شود؛ `.gitignore` و کنترل بهداشت مخزن این را تضمین می‌کنند.
- ماژول‌های خارج از محدوده (اسکن پورت، breach، dark web، خزش اجتماعی) عمداً پیاده‌سازی نشده‌اند
  و درخواستشان با خطای `unsupported_modules` رد می‌شود.

## استقرار

### محلی (بدون Docker)

```bash
python3 doctrine/api.py --port 8001
python3 osint/app.py --port 8002
python3 hub/core.py --serve --port 8000
python3 -m http.server 8080 --directory web
```

### Docker Compose

`docker compose up -d` چهار سرویس را بالا می‌آورد: doctrine (8001)، osint (8002)، hub (8000)، web (8080).

### GitHub Pages

پوشه‌ی `web/` بدون backend کار می‌کند. در تنظیمات مخزن، Pages را روی همان شاخه و پوشه‌ی `web` تنظیم کن.
`robots.txt` و `sitemap.xml` از قبل آماده‌اند.

## توسعه

- هر سرویس یک `--selftest` دارد؛ `scripts/selftest_all.py` همه را اجرا می‌کند.
- تست‌ها آفلاین‌اند و به شبکه/توکن نیاز ندارند.
- برای افزودن گام جدید به هاب: یک شاخه در `run_stage` و یک ورودی در `intents` پیکربندی اضافه کن.
